# Работа над Util Maker

При первом входе прочитай [общее ТЗ](docs/specification.md), [правила проекта](docs/development-guide.md) и [правила задач](docs/task-workflow.md). Подробности по компоненту найди в [карте блоков](docs/blocks/README.md).

1. На Ubuntu из корня checkout выполни `make dev-setup`. Требуются GNU Make, доступ к Linux Docker Engine и сеть для первой загрузки зависимостей. Репозиторий должен быть доступен Docker по пути checkout для bind mount.
2. Работай с примонтированными исходниками через `make dev-shell` или `make dev-run CMD="cargo --version"`. Повторяемые команды оформляй отдельными целями Makefile. Файлы создаются с UID/GID пользователя. Cargo и npm используют кэш рабочего каталога.
3. Если пользователь назвал карточку, работай по ней. По команде «бери следующую задачу» или `$next-task` выбери одну карточку по порядку из [сводного списка](docs/tasks/README.md). Если указан блок («бери следующую задачу по plugins/screenshot»), выбирай только в его очереди. Следуй [skill next-task](.agents/skills/next-task/SKILL.md) при выборе и передаче на ревью. Меняй статус в карточке и в строке её очереди одним изменением. Выполняй Linux-проверки в контейнере. Для сборки frontend агенту нужна явная просьба пользователя.
4. Для проверки на Windows передай ревизию, команду локальной сборки и короткие шаги с ожидаемым результатом. Установщик собирает и запускает пользователь на своей машине. В задаче отдельно указывай, что проверено на Linux и что ожидает проверки на Windows.

## Заголовки коммитов

Используй формат `feat(<область>): <что сделано>`. Область указывает компонент, которому принадлежит результат. После двоеточия кратко опиши конкретное изменение на русском, чтобы строка была понятна в `git log --oneline`.

- Для ядра, оболочки, SDK и пакетов используй `core`, `desktop`, `sdk`, `packages`. Для адаптера указывай ОС, например `platform/windows`.
- Для очереди `plugins/<имя>` используй область `plugin/<имя>`. Она показывает, какой именно плагин изменился. Для адаптеров перевода используй `plugin/translator/providers`.
- Документация и тесты одного компонента получают его область. Для общепроектной документации используй `docs`. Если один результат затрагивает несколько компонентов, укажи владельца результата по карточке.

```text
feat(core): сохранены остальные шорткеи при переносе сочетания
feat(packages): добавлен экспорт подписанного пакета
feat(plugin/screenshot): добавлена отмена последней аннотации
feat(plugin/translator/providers): добавлена обработка ошибки квоты Google
```
