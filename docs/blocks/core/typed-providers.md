# ТЗ. Типизированные провайдеры микроприложений

**Результат первой версии.** Пользователь один раз подключает личный и рабочий Google Диск и сервер Nextcloud. В «Скриншотах» он выбирает «Рабочий Google Диск» и папку для PNG. Другое микроприложение может использовать тот же аккаунт со своей папкой или выбрать Nextcloud. Добавление новой реализации хранилища не требует выпуска новой версии приложений-потребителей.

## Архитектурное решение

В Host API 1.1 пакет может объявить точку расширения, а отдельный подписанный пакет — реализовать её через `provides`. Такой вклад привязан к конкретному родителю и точке. Выбор `single` общий для этой точки. Он подходит переводчику, но не выражает выбор двух разных аккаунтов двумя потребителями. [Действующий контракт расширений](extensions.md)

| Вариант | Последствие |
| --- | --- |
| Размещать адаптеры и авторизацию внутри каждого приложения | Просто для одного потребителя. Подключение аккаунтов и поддержку сервисов пришлось бы повторять в каждом следующем. |
| Делать каждый сервис расширением каждого потребителя | Сохраняется текущий IPC. Каждый вклад должен знать ID всех приложений, которые захотят с ним работать. |
| Выбирать провайдер по типу и использовать его собственные расширения | Появляются каталог типов и привязки. Один пакет сервиса обслуживает несколько потребителей, а ядро по-прежнему контролирует каждый межпроцессный вызов. |

Выбран третий вариант. В первой поставке участвуют скриншотер, отдельный пакет «Файловые хранилища» и два независимо обновляемых пакета реализаций. Стрелки показывают логический маршрут. Процессы запускает и связывает хост.

```text
Приложение со слотом file-storage (первое — «Скриншоты»)
  → провайдер типа file-storage («Файловые хранилища»)
    → выбранная реализация (Nextcloud или Google Диск)
      → именованное подключение и папка этого потребителя
```

## Манифест и совместимость

Целевой Host API — `1.2.0`, версия схемы манифеста — `1`. Новые поля ниже описывают требуемое расширение SDK. Пакет с новыми декларациями указывает `hostApi: ">=1.2.0 <2.0.0"`, чтобы старый хост отклонил несовместимую версию до активации.

| Поле | Семантика |
| --- | --- |
| `type` | `app` — приложение, `provider` — пакет провайдера. Без поля действуют прежние правила для приложения или legacy-вклада с `provides`. Переводчик и его пакеты сохраняют прежние регистрацию, настройки, выбор и вызовы. |
| `providerSlots[]` | Потребитель объявляет локальный стабильный `id`, принимаемый `contract`, диапазон `interfaceVersion` и признак `required`. Хранилище у «Скриншотов» опционально. |
| `providerService` | Родительский пакет типа `provider` публикует тип (`contract`), точную semver-версию `contractVersion` и `pointId` своей точки реализаций. Несколько установленных поставщиков одного контракта различаются по ID пакета. |
| `extensionPoints` и `provides` | Пакет сервиса объявляет точку с новым правилом `selection: "binding"`. Пакет реализации типа `provider` вносит ровно адресованный вклад через существующие `moduleId`, `pointId`, `contract`, `interfaceVersion`. Его настройки и секреты принадлежат его ID. |

В примерах ниже приведены поля, которые связывают три подписываемых манифеста.

```json
[
  {"id":"org.utilmaker.screenshot","type":"app","providerSlots":[{"id":"save-target","contract":"util-maker.file-storage","interfaceVersion":">=1.0.0 <2.0.0","required":false}]},
  {"id":"org.utilmaker.file-storage","type":"provider","providerService":{"contract":"util-maker.file-storage","contractVersion":"1.0.0","pointId":"storage-backend"},"extensionPoints":[{"id":"storage-backend","name":"Реализация хранилища","contract":"util-maker.file-storage.backend","contractVersion":"1.0.0","selection":"binding","required":true}]},
  {"id":"org.utilmaker.file-storage.nextcloud","type":"provider","provides":[{"moduleId":"org.utilmaker.file-storage","pointId":"storage-backend","contract":"util-maker.file-storage.backend","interfaceVersion":">=1.0.0 <2.0.0","name":"Nextcloud"}]}
]
```

Слоту соответствует публичный контракт сервиса, вкладу — контракт точки реализации. Обе пары проверяются независимо с учётом версий. Сервис и вклад могут иметь пустой `actions`. SDK требует у потребителя `providers.call`, у владельца точки — `extensions.read` и `extensions.call`. Запрещены неизвестный тип, дубли слотов, ссылка сервиса на отсутствующую собственную точку, вклад с собственными точками, циклы и дальнейшая передача вызова из реализации. Этот маршрут добавляет одну типизированную связь. Действующие ограничения для прежних `provides` и `single` сохраняются.

## Настройки, данные и интерфейс

| Сущность и владелец | Что сохраняется |
| --- | --- |
| Каталог, ядро | Типы, версии, установленные сервисы и реализации из проверенных манифестов. Перечисление работает без сети и запуска процессов. Установка, отключение, обновление, откат и удаление сразу меняют доступность. |
| Именованное подключение, пакет реализации | Неизменяемый `connectionId`, ID сервиса и реализации, отображаемое имя, несекретные параметры и состояние авторизации. Два аккаунта одного сервиса или два сервера Nextcloud создают две записи. Секреты адресуются по ID реализации и подключения через хранилище ОС. |
| Привязка, хост от имени потребителя | Ключ `(consumerId, slotId)`, ID сервиса, реализации и подключения, параметры назначения данного слота. Для файлового хранилища это папка. Чтение чужих привязок через API потребителя запрещено. |

1. В разделе «Провайдеры» видны тип, установленные реализации, состояние и именованные подключения. Пользователь добавляет аккаунт, проверяет соединение, переименовывает, повторно авторизует и удаляет подключение. Новые реализации появляются по манифесту. Доступ к настройкам не требует действий или шорткеев в трее.
2. В приложении со слотом показаны только установленные совместимые провайдеры нужного типа и их подключения, сгруппированные по сервису и реализации. Рядом с неготовым подключением видны причина и переход в настройки. При пустом списке доступны установка пакета и создание подключения. Выбор и папка сохраняются для конкретного слота.
3. При переименовании ID сохраняется. Смена учётной записи на другую создаёт новое подключение. Перед удалением показать использующие его приложения и последствие. Удаление очищает секреты этого подключения, затронутые слоты показывают «Требуется подключение». Новое подключение с таким же именем привязывается только по выбору пользователя.
4. Отключение или несовместимое обновление сервиса или реализации сохраняет привязку с причиной недоступности. После восстановления той же совместимой идентичности и действительного подключения она работает снова. Успешное обновление и откат совместимых пакетов сохраняют аккаунты, папки и назначения. При удалении реализации применить очистку её секретов. Удаление потребителя снимает только его привязки. При прерванном изменении профиля хост восстанавливает согласованное состояние.

Режим «Локальная папка» у скриншотера выбран по умолчанию, включая существующие профили. Облачная отправка начинается только по явной команде сохранения в выбранное назначение. При потере подключения UI предлагает повтор, настройку или явное сохранение локально. Буфер обмена и захват остаются доступны офлайн. ## Маршрутизация и жизненный цикл

- Для активного вызова потребитель с возможностью `providers.call` обращается через `host.call` к новому методу `provider.invoke`, указывая свой `slotId`, операцию и её данные. Хост извлекает потребителя из контекста, находит его явно сохранённую привязку и проверяет оба контракта, состояния пакетов и подключения. Клиент не может передать чужие реквизиты, подменить аккаунт, папку или произвольный ID процесса.
- Хост запускает пакет сервиса и передаёт ему контекст привязки. Сервис через `extensions.call` и `extension.invoke` вызывает вклад своей точки `binding`. Для такой точки ядро берёт реализацию **из контекста текущего вызова**. Два параллельных сохранения проходят в свои аккаунты. Старый глобальный выбор `single` переводчика в этих вызовах не участвует.
- Вложенные операции получают отдельные `callId`, общий предельный срок и распространение отмены. Связь активна до завершения команды сохранения, даже если исходный вызов захвата уже закончился. На границе команды редактора хост открывает новый проверенный контекст сохранения. Ограничения по времени сетевых операций задаёт контракт хранилища. Вход в аккаунт в настройках имеет отдельную пользовательскую сессию.
- Сбой реализации изолируется по её ID. При отсутствии привязки, несовместимости, отключении, истечении авторизации, сетевой ошибке и неопределённом результате приложение получает различимые причины. Другая учётная запись автоматически не выбирается. Поздний ответ после отмены не меняет состояние нового вызова.
- Приложение передаёт данные только в пределах полномочий слота. Вложенный процесс получает собственные возможности и доступ к секрету только текущего подключения. Передача крупных данных описана в контракте хранилища. Журнал содержит ID вызова, пакета, категорию и длительность. Содержимое файла, токены, пароли, полные пути и авторизационные URL в диагностику не попадают. В простое нет процессов провайдеров, сетевых проверок и фоновой синхронизации.

## Граница первой поставки и приёмка

Первый тип — `util-maker.file-storage` v1. Операция для потребителя — сохранение одного файла. Реализации — Nextcloud и Google Диск. Dropbox и ownCloud смогут поставляться отдельными совместимыми пакетами. Системы перевода продолжают использовать действующий контракт расширений.

| Среда | Наблюдаемый результат |
| --- | --- |
| Linux, изолированный контейнер | Два потребителя (второй — тестовый модуль), два аккаунта одной реализации и разные папки. Параллельные записи доставляются в выбранные назначения. Попытки подменить слот, подключение, ссылку на данные и обойти отключение отклоняются до обращения к сервису. |
| Linux, тестовые HTTP-серверы и подписанные пакеты | Оба адаптера проходят единый набор проверок записи. Обновление, откат, недоступная реализация, обрыв после подтверждения сервером и перезапуск хоста сохраняют изоляцию и дают объяснимый результат. Обычный пакет и расширения переводчика продолжают работать. |
| Windows 11 x64, пользователь | По переданной ревизии локально собрать `make build-windows`. Установить три подписанных пакета, подключить Nextcloud и два Google-аккаунта. Сохранить и открыть PNG с аннотацией в каждом назначении. Проверить раздельные папки для двух потребителей, смену аккаунта, отключение, обновление, отзыв доступа, локальное сохранение и копирование без сети. |
