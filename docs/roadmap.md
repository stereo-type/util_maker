# План развития Util Maker

Цель первой поставки — на чистой Windows 11 x64 пользователь устанавливает Util Maker, вызывает из любой рабочей программы «Скриншоты» и «Переводчик» и может обновить каждый инструмент отдельно. Требования к поставке закреплены в [общем ТЗ](specification.md).

В прототипе уже работают трей, вызов контрольного процесса по шорткею и проверка подписи пакета. Для скриншотов есть библиотека обрезки и аннотаций, для переводчика — логика выбора текста и HTTP-адаптеры Яндекса и Google. Ближайший шаг — подключить эти части через существующий контракт плагинов. [Архитектура проекта](../README.md) · [История прототипа](tasks/blocks/core/README.md)

## 1. Подготовить два исполняемых плагина и экспорт пакетов

Три направления можно брать параллельно. У каждого плагина появятся собственный манифест и процесс. Хост сможет вызвать объявленное действие через SDK и получить осмысленный ответ, в том числе при недоступном источнике данных. Отдельно разработчик сможет экспортировать подготовленный каталог плагина в подписанный архив, который принимает существующая проверка.

Для этого уже заведены три карточки. [Процесс «Скриншотов»](tasks/blocks/plugins/screenshot/module-process.md) · [Процесс «Переводчика»](tasks/blocks/plugins/translator/module-process.md) · [Экспорт .umpkg](tasks/blocks/packages/export-package.md)

## 2. Устанавливать и обновлять инструменты из настроек

Пользователь выбирает локальный пакет, видит издателя и действия, устанавливает его и назначает шорткей. Менеджер пакетов отвечает за проверку, переключение версии и откат. Ядро сохраняет назначения по ID действия, а desktop-хост строит меню и страницы настроек по активным манифестам. Интеграцию можно начать на двух версиях контрольного плагина.

Этап можно принять, когда после обновления одного плагина второй продолжает работать, а после прерванного обновления восстанавливаются согласованные версия и настройки. Редактор предупреждает о передаче занятого сочетания и запрещает назначение системных сочетаний Windows. [Пакеты](blocks/packages/README.md) · [Шорткеи ядра](blocks/core/hotkeys.md) · [Настройки](blocks/desktop/settings.md)

## 3. Довести оба действия до результата в Windows

SDK и ядро предоставляют плагинам контекст исходного приложения и доступ к разрешённым операциям. Windows-адаптер отвечает за получение кадра и выделения, буфер обмена и хранение секретов. После согласования этих контрактов оба плагина можно разрабатывать параллельно и проверять на тестовых адаптерах. [SDK](blocks/sdk/README.md) · [Адаптер Windows](blocks/platform/windows/README.md)

| Направление | Результат для пользователя |
| --- | --- |
| [Скриншоты](blocks/plugins/screenshot/README.md) | По шорткею пользователь выделяет область, добавляет стрелку или рамку и вставляет результат в Paint. Размер и положение аннотаций сохраняются на мониторах с разным DPI. Отмена сохраняет прежний буфер. |
| [Переводчик](blocks/plugins/translator/README.md) и [провайдеры](blocks/plugins/translator/providers/README.md) | Слово можно выделить до или после шорткея. Пользователь получает перевод рядом с исходным текстом, настраивает собственные ключи Яндекса и Google и меняет активный сервис с сохранением шорткея. При отмене ожидания выделения или вызове в известном парольном поле текст остаётся на устройстве. |

## 4. Принять первую поставку Windows

В установщик входят хост и два независимо обновляемых пакета. Пользователь собирает установщик из переданной ревизии локально через `make build-windows` и проверяет его в своей Windows-сессии. Приёмка охватывает все 11 сценариев общего ТЗ, включая доступность настроек с клавиатуры, восстановление после сбоя и подключение стороннего модуля с двумя действиями по документации SDK. В протокол входят измеренные память и CPU в простое, холодный отклик и возврат ресурсов после повторных вызовов. [Сквозная приёмка](blocks/README.md#сквозная-приёмка) · [Методика замеров](blocks/core/diagnostics.md) · [Передача на Windows](development-guide.md#передача-на-windows)

## После первой поставки

Расширение штатной поставки включает три независимых пакета. [Текст с экрана](blocks/plugins/screen-ocr/README.md) распознаёт выбранную область. [QR-коды](blocks/plugins/qr-code/README.md) показывают код из текста и считывают его с экрана. [Пипетка цвета](blocks/plugins/color-picker/README.md) копирует значение выбранного пикселя. Настройки, именование действий и критерии приёмки определены в ТЗ каждого плагина.

Переносимую логику всех трёх можно проверять параллельно на эталонных данных. Общая зависимость сквозной приёмки — доступ к пикселям из отдельного процесса. Для каждого пакета проверить установку в чистом профиле, вызов из трея и шорткеем, отмену, освобождение ресурсов и обновление с сохранением назначений. Пользователь выполняет локальную сборку хоста через `make build-windows` и ручную проверку в Windows 11 x64. [Контракт доступа к кадру](blocks/sdk/README.md#доступ-плагина-к-пикселям-кадра) · [Формат пакета](blocks/packages/package-format.md)

### Плагины-расширения микроприложений

После первой поставки микроприложение сможет объявлять точки расширения, а
независимые подписанные пакеты — подключаться к ним. Первый сценарий —
переводчик: Яндекс и Google станут отдельными плагинами, которые можно
устанавливать, обновлять и удалять без обновления переводчика. Контракт
манифеста, вызов дочернего процесса, установка, интерфейс и миграция
провайдеров разложены на последовательные карточки: [SDK](tasks/blocks/sdk/extension-manifest.md) ·
[ядро](tasks/blocks/core/nested-extensions.md) · [пакеты](tasks/blocks/packages/extension-packages.md) ·
[интерфейс](tasks/blocks/desktop/extension-packages-ui.md) ·
[переводчик](tasks/blocks/plugins/translator/provider-extension-point.md) ·
[пакеты провайдеров](tasks/blocks/plugins/translator/providers/provider-packages.md). Общий контракт описан в
[ТЗ плагинов-расширений](blocks/core/extensions.md).

Для возможных портов на Ubuntu и macOS сохраняем переносимость ядра и формата пакета. Решение о конкретном порте принимается отдельно. Первой задачей такого порта будет проверка системных возможностей для трея, глобального шорткея, захвата и буфера на выбранной ОС. [Границы платформы](specification.md#1-назначение-и-границы)

## Как выделить следующую задачу

Выберите один проверяемый результат этапа и компонент, который за него отвечает. Например, для скриншотов получение кадра с координатами монитора относится к `platform/windows`, а отмена аннотации в редакторе — к `plugins/screenshot`. Перед созданием карточки проверьте очередь владельца. В карточке укажите этап, ссылку на ТЗ блока, необходимые зависимости и критерий приёмки. Статусы ведутся в [очередях задач](tasks/README.md) по [правилам работы с карточками](task-workflow.md).
