# Исполнять запросы возможностей только в контексте активного вызова

**Статус** — 👁️ На ревью

[Этап 3 плана развития](../../../roadmap.md#3-довести-оба-действия-до-результата-в-windows) · [ТЗ блока](../../../blocks/core/README.md)

Встроить двусторонний обмен в `ModuleProcess` и реальный маршрут вызова. Хост закрепляет внешний источник до показа собственных окон и передаёт соответствующему адаптеру контекст модуля, действия и вызова. Для старта использовать подменную ОС.

**Зависимости для старта** — [Дать модулю доступ к возможностям хоста во время invoke](../sdk/host-capabilities.md).

## Критерии приёмки

- [x] Два одновременно работающих модуля получают только заявленные возможности и свои контексты, кадры и секреты. Подмена чужого ID или просроченной ссылки получает отказ.
- [x] Вызов из меню использует последнее внешнее окно, шорткей — источник в момент события. При потере источника модуль получает определённый исход.
- [x] Выход, отмена и падение освобождают буферы, подписки и дочерние процессы. Поздний ответ отбрасывается, зависший процесс останавливается в срок из ТЗ, второй модуль остаётся доступен.

## Что сделано

- `HostDispatcher` закрепляет `CallSession` (`moduleId + actionId + callId`, источник и опциональная непрозрачная ссылка) и выдаёт кадры только владельцу. `frame.release` проверяет `callId`, срок `expiresInMs` и освобождает буфер; `finish_call`/`Drop` освобождают все оставшиеся кадры.
- `InvocationContext::tray` фиксирует последнее внешнее окно до меню, `hotkey` — источник в момент события. Потерянный источник даёт `CONTEXT_LOST`, необъявленная возможность — `CAPABILITY_DENIED`, просроченный кадр — `BUFFER_EXPIRED`.
- `PlatformHost` получает только `CallSession`; Win32-дескрипторы и адреса памяти в публичный контракт не входят. `Registry::invoke_session` вызывает `begin_call`/`finish_call` на любом исходе, включая отмену и падение.
- Два модуля одновременно получают разные контексты, кадры и секреты из общего подменного адаптера.

## Проверка

Linux, контейнер `util-maker-dev:local`:

- `cargo test -p util-maker-core --test host_dispatch` — 4/4:
  - два активных вызова получают свои кадры и секреты; попытка освободить чужой кадр даёт `CAPABILITY_DENIED`;
  - после `finish_call` платформенный адаптер получает освобождение кадра;
  - просроченная ссылка даёт `BUFFER_EXPIRED`;
  - потерянный источник даёт `CONTEXT_LOST`, необъявленная возможность — `CAPABILITY_DENIED`;
  - реальный процесс `fixture-module` получает кадр через `host.call`.
- `cargo test -p util-maker-core --test host_capabilities` — 3/3 для контракта SDK; `make check` — 106 тестов, Clippy и rustfmt без замечаний.

Реальная передача Win32-кадра и подписок подключается через `PlatformHost` в задачах платформы; Linux-проверка использует подменную ОС.
