# Изолировать необработанную ошибку плагина и сообщить о сбое оболочке

**Статус** — 👁️ На ревью

[Этап 4 плана развития](../../../roadmap.md#4-принять-первую-поставку-windows) · [ТЗ ядра](../../../blocks/core/README.md) · [Правила диагностики](../../../blocks/core/diagnostics.md)

Довести существующую обработку ошибок в `ModuleProcess` до публичного маршрута вызова через `Registry`. Оболочке нужно знать, какой именно плагин завершился, чтобы показать пользователю причину и предложить отключить его. Ядро определяет наблюдаемый исход по IPC и состоянию дочернего процесса. Исключение внутри чужого процесса может завершить его до отправки ответа.

**Зависимости для старта** — можно начинать на текущей ревизии с `fixture-module` и контрольным плагином.

## Критерии приёмки

- [x] Аварийный выход при инициализации или во время действия и внутренняя ошибка, о которой плагин успел сообщить по RPC, дают по одному конечному исходу на вызов. В оболочку приходят ID модуля и действия, машинная категория и понятная причина в пределах сведений хоста. Отмена пользователем и ожидаемая прикладная ошибка различимы со сбоем процесса.
- [x] При двух активных плагинах падение первого освобождает ресурсы его вызова. Второй продолжает отвечать. Хост остаётся в трее, а следующий явный вызов первого плагина возможен, пока пользователь его не отключил.
- [x] Сообщение оболочке позволяет однозначно адресовать отключение сбойному модулю даже при поступлении результата другого вызова. Текст исключения, необработанный stderr, содержимое выделения и ключи не попадают в сообщение пользователю или журнал.

## Что сделано

- `InvokeFailure` содержит `callId`, `moduleId`, `actionId`, имя действия, длительность, RPC-код, машинную категорию (`module_crashed`, `module_reported_error`, `cancelled`, `module_timeout`, `protocol_violation`, `module_disabled`, `module_not_found`, `action_unavailable`) и очищенное сообщение.
- `Registry::invoke_detailed`, `invoke_detailed_with_host` и `invoke_session` возвращают этот исход; старые `invoke`/`invoke_with_host` совместимы и отдают `CoreError`.
- Ошибки записи и запуска журналируются ровно одним итогом на вызов. stderr плагина и запоздалые IPC-сообщения проходят через `sanitize`, текст исключения не копируется в публичное сообщение целиком.
- Падение или отключение одного модуля не меняет состояние второго; повторный явный вызов аварийного модуля разрешён, пока пользователь его не отключил.

## Проверка

Linux, контейнер `util-maker-dev:local`:

- `cargo test -p util-maker-core --test failure_isolation` — 5/5:
  - аварийный выход во время действия даёт `module_crashed` с точным `moduleId/actionId/callId`; повторный вызов снова доходит до процесса, автоматического отключения нет;
  - ошибка, возвращённая по RPC, даёт `module_reported_error` и RPC-код `2001`; `Authorization` и тестовый секрет не попали ни в сообщение, ни в журнал;
  - падение при инициализации с секретом в stderr не раскрывает исходный stderr;
  - одновременно падающий плагин не мешает контрольному модулю ответить;
  - запоздалое сообщение с чужим `id` и заголовком `Authorization` попадает в журнал только после `sanitize`: секрет не найден.
- `make check` — 106 тестов, Clippy и rustfmt без замечаний.

Для Windows остаётся ручная проверка сообщения и кнопки «Отключить плагин» по [карточке desktop](../desktop/package-management.md) на ревизии из этого изменения.
