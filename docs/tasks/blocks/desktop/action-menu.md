# Строить трей и список микроприложений по активным манифестам

**Статус** — 👁️ На ревью

[Этап 2 плана развития](../../../roadmap.md#2-устанавливать-и-обновлять-инструменты-из-настроек) · [ТЗ блока](../../../blocks/desktop/README.md)

В `apps/desktop` заменить фиксированные пункты и вызов `run_control_action` данными реестра. Показ страницы плагина, меню трея и вызов действия должны работать для произвольного ID. Для начала использовать два тестовых манифеста и существующий `Registry`. При интеграции подключить каталог установленных версий.

**Зависимости для старта** — можно начинать на текущей ревизии.

**Для сквозной проверки** — [Обновлять реестр действий из каталога активных пакетов](../core/installed-actions.md).

## Критерии приёмки

- [x] Имя, иконка, версия, включённость и список действий соответствуют активному манифесту. Остановленные процессы остаются остановленными при открытии списка.
- [x] Пункт меню передаёт пару ID в ядро. Установка или отключение пакета обновляет список и трей без перезапуска. Закрытие настроек освобождает окно и оставляет трей доступным.

## Что сделано

- `CatalogState` читает каталог `modules` рядом с исполняемым файлом (или `UTIL_MAKER_MODULES_DIR`), проверяет манифест и точку входа и один раз заполняет `Registry`; при чтении списка процессы модулей не запускаются.
- Меню трея пересобирается из `Registry::actions()`: пункты действий передают в ядро пару `moduleId + actionId`, а статические пункты остались только для настроек, паузы, перерегистрации и выхода.
- Страница микроприложений получает имя, версию, издателя, иконку из манифеста и действия через `Registry`. Иконка передаётся в WebView как data URL, поэтому не требует доступа к файловой системе из JavaScript.
- Команды `invoke_plugin_action` и `refresh_plugins` работают с произвольными ID; отключение пакета вызывает `Registry::set_enabled`, после чего список действий и меню трея обновляются без перезапуска.
- Состояние отключённых пакетов хранится в `packages.json`, рядом с профилем приложения.

## Проверка

Linux, контейнер `util-maker-dev:local`:

- `make check` — 109 тестов, Clippy и rustfmt без замечаний.
- `cargo test -p util-maker-desktop` — 4/4:
  - два тестовых манифеста дают два действия, маркер запуска процесса не появился;
  - отключённый пакет исчезает из списка действий, второй остаётся доступным;
  - иконка манифеста кодируется в `data:image/png;base64,...`;
  - существующий тест журнала продолжает проходить.
- Встроенный JavaScript проверен `node --check`.

На Windows пользователь проверяет после установки:

1. Открыть трей: пункт `Контрольный модуль — Проверить связь` и настройки доступны.
2. Открыть настройки: у контрольного модуля видны иконка, версия `0.4.1`, действие `Проверить связь`; вызов из трея и из карточки показывает результат.
3. Отключить контрольный модуль в настройках: пункт исчезает из трея; включить обратно и убедиться, что пункт вернулся без перезапуска.
4. Закрыть настройки: трей остаётся доступным, повторный запуск открывает настройки существующего экземпляра.

Ревизия для Windows — ``33bb409``; сборка установщика — `make build-windows`. Второй тестовый модуль для проверки нескольких действий подкладывается в каталог `modules` рядом с установленным приложением вручную до появления импорта пакетов.
