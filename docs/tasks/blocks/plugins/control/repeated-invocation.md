# Проверить повторный вызов контрольного действия

**Статус** — ✅ Выполнена

**Основание** — [ТЗ контрольного плагина](../../../../blocks/plugins/control/README.md) и [контракт SDK](../../../../blocks/sdk/README.md).

Контрольный плагин уже отвечает на `ping` из отдельного процесса. Нужно
закрепить автоматической проверкой требование ТЗ: после завершения процесса
действие можно вызвать снова, каждый вызов обслуживается новым процессом, а
ответ содержит собственный `callId`, источник вызова и PID. В README плагина
уточнить фактическую точку входа и способ проверки на Linux.

**Зависимости для старта** — существующие SDK, ядро и контрольный плагин.
Ручная проверка на Windows выполняется при следующей приёмке поставки.

## Критерии приёмки

- [x] На Linux тест трижды вызывает `org.utilmaker.control / ping` через реестр ядра и получает успешный ответ.
- [x] У каждого вызова уникальный `callId`, совпадающий с `data.callId`; `data.source` соответствует источнику вызова, PID отличается от предыдущего.
- [x] После каждого вызова процесс контроля отсутствует в `/proc`, то есть повторный вызов не переиспользует зависший или завершённый процесс.
- [x] README плагина указывает точку входа из манифеста, поля ответа, обработку неизвестного действия и команду проверки.
- [x] На Windows действие из трея и шорткеем вызывается повторно после завершения процесса, оба результата видны пользователю.

## Проверка

Linux, контейнер `util-maker-dev:local`:

- `make check` — версия согласована, `cargo fmt --check` без изменений, Clippy без предупреждений, 64 теста пройдены.
- Целевая проверка `make dev-run CMD="cargo test -p util-maker-core --test control_module_ipc"` — 5 тестов пройдены, включая `control_action_can_be_invoked_repeatedly` (0.13 с).
- Новый тест трижды вызывает `ping` через реестр: PID процессов различаются, `callId` уникальны, `/proc/<pid>` после ответа отсутствует.

Ручная проверка на Windows остаётся в очереди приёмки.

Пользователь подтвердил повторный вызов на Windows; карточка закрыта.
