# Добавить исполняемый процесс плагина «Переводчик»

**Статус** — 👁️ На ревью

[Этап 1 плана развития](../../../../roadmap.md#1-подготовить-два-исполняемых-плагина-и-экспорт-пакетов)

**Основание** — [ТЗ переводчика](../../../../blocks/plugins/translator/README.md) и [контракт SDK](../../../../blocks/sdk/README.md).

В каталоге плагина уже реализованы выбор текста и HTTP-адаптеры. Добавить манифест и точку входа для вызова `org.utilmaker.translator / translate` отдельным процессом. Обработка вызова использует существующий контроллер выбора текста. Привязка к UI Automation, окно результата и проверка реальными ключами относятся к последующей интеграции.

**Зависимости для старта** — существующие SDK и библиотека переводчика. Для проверки границы процесса достаточно Linux без ключей провайдеров.

## Критерии приёмки

- [x] Манифест читается SDK, объявляет действие «Перевести текст» и точки входа с именами собираемых файлов. На Linux запускается отдельный процесс и подтверждает свой ID при `initialize`.
- [x] Проверка через stdio вызывает `translate`. При недоступном контексте источника обработчик завершает запрос с явной причиной и сохраняет нулевое число HTTP-запросов. Этот путь можно проверить офлайн.
- [x] Для неизвестного действия процесс возвращает `ACTION_NOT_FOUND`, а на `shutdown` штатно завершается. В README плагина приведена воспроизводимая проверка через Makefile.

## Что сделано

- `plugins/translator/manifest.json` — ID `org.utilmaker.translator`, действие `translate` («Перевести текст»), точки входа `translator-module.exe` и `translator-module`; манифест проходит `Manifest::validate`.
- `plugins/translator/src/main.rs` — процесс `translator-module` на SDK: подтверждает ID на `initialize`, принимает `invoke`, возвращает `ACTION_NOT_FOUND` для неизвестного действия и завершается по `shutdown`.
- `plugins/translator/src/lib.rs` — у `BlockReason` появились стабильный код и пользовательское объяснение для ответа процесса.
- `plugins/translator/Cargo.toml` — добавлена цель `[[bin]] name = "translator-module"`.
- `Makefile` — `bump-version` обновляет версию манифеста переводчика, а `check-version` сверяет оба штатных манифеста с версией workspace.
- `crates/core/tests/translator_module_ipc.rs` — проверка манифеста и настоящего stdio-процесса.
- `plugins/translator/README.md` и `plugins/README.md` — контракт процесса, команды проверки и актуальное состояние плагина.

Обработчик использует `SelectionController`. Пока снимок источника не подключён к UI Automation, действие возвращает `outcome = "blocked"`, `reason = "context-lost"` и `httpRequests = 0`; провайдер не вызывается. Ручной ввод, окно результата и реальные ключи остаются в следующих задачах.

## Проверка

Linux, контейнер `util-maker-dev:local`:

- `make check` — версия 0.4.3 согласована, rustfmt и Clippy без замечаний, **127 тестов** пройдено.
- `cargo build --workspace --bins` — собран процесс `translator-module` вместе с остальными бинарниками workspace.
- `cargo test -p util-maker-core --test translator_module_ipc` — **5/5**: манифест, рукопожатие, `translate` без источника, `ACTION_NOT_FOUND`, `shutdown`.
- `cargo test -p util-maker-translator --lib` — **7/7** существующих переходов контроллера выбора.

На Windows в этой карточке ручная проверка не требуется: процесс не содержит Win32-кода и использует переносимый stdio SDK. Имя `translator-module.exe` объявлено в манифесте; упаковка и установка плагина выполняются отдельной задачей.
